# Security Check

HTML/JS 파일 하나를 4가지 보안 관점에서 점검하고, 문제의 심각도를 3단계로 분류해 보고하는 스킬이다.

## 언제 쓰는가

사용자가 "보안 점검", "security check"라고 말하거나, 방금 만든/수정한 HTML·JS 파일에 초보적인 보안 실수가 없는지 확인하고 싶어할 때 사용한다. 파일을 명시하지 않으면 최근 대화에서 다루던 HTML/JS 파일을 대상으로 삼되, 애매하면 사용자에게 어떤 파일을 점검할지 확인한다.

## 점검 절차

### 1. 원시 진단 실행

4가지 관점 모두 정규식으로 후보를 찾아내는 방식이라, 사람이 눈으로 훑는 것보다 스크립트로 먼저 훑어서 놓치는 줄이 없도록 하는 게 안전하다. 반드시 번들된 스크립트를 먼저 실행해 원시 후보 목록을 얻는다:

```bash
python .claude/skills/security-check/scripts/check_security.py <html_or_js_file>
```

스크립트는 JSON을 출력한다. 이 JSON은 "후보"일 뿐 최종 판정이 아니다 — 한 줄 단위 정규식 검사라 오탐(placeholder 값, 안전한 정적 문자열 등)과 미탐(여러 줄에 걸친 코드)이 있을 수 있다. 각 후보를 실제 코드 맥락과 함께 다시 읽고, 아래 표에 따라 이 스킬을 실행하는 모델이 직접 심각도를 판단한다.

### 2. 심각도 분류

스크립트가 찾아낸 후보를 아래 표에 따라 분류한다. 판단이 애매한 경우 페이지는 정상 동작하지만 더 다듬을 여지가 있다는 뉘앙스로 🟢 제안으로 내린다.

| 항목 | 판정 기준 | 등급 | 이유 |
|---|---|---|---|
| 하드코딩된 비밀번호·API 키 | `hardcoded_secrets`에 항목이 있고 `looks_like_placeholder`가 false (실제 값처럼 보임) | 🔴 심각 | 코드를 볼 수 있는 누구나 비밀번호·키를 그대로 획득 가능 |
| 하드코딩된 비밀번호·API 키 | `looks_like_placeholder`가 true (예: `"YOUR_API_KEY"`, `"changeme"`, 빈 문자열) | 🟢 제안 | 지금 당장 노출된 실제 값은 아니지만, 실제 배포 전 값 채우는 방식을 점검할 것을 권고 |
| innerHTML XSS | `innerhtml_xss`에 항목이 있고 `likely_user_input`이 true (입력값·URL 파라미터·쿠키 등이 이스케이프 없이 흘러들어감) | 🔴 심각 | 공격자가 입력만으로 임의 스크립트 실행 가능 |
| innerHTML XSS | `innerhtml_xss`에 항목이 있지만 `likely_user_input`이 false (개발자가 만든 고정/신뢰 데이터로 보임) | 🟡 주의 | 지금은 안전해 보이지만 나중에 사용자 입력이 섞여도 알아채기 어려운 패턴 — `textContent`/`createElement` 사용 권장 |
| console.log 민감정보 노출 | `console_log_sensitive`에 항목 존재 | 🟡 주의 | 프로덕션 콘솔·에러 리포팅 도구에 비밀번호·토큰 등이 남을 수 있음 (즉시 외부 유출은 아니라 심각까지는 아님) |
| http:// 외부 요청 | `http_external`에 항목이 있고 `is_local`이 false이며 `context_hints`에 `fetch`/`xmlhttprequest`/`axios`/`.open(`/`websocket`처럼 실제 데이터 송수신 흔적이 있음 | 🔴 심각 | 평문 통신으로 전송 데이터(자격증명 등)가 도청·변조될 수 있음 |
| http:// 외부 요청 | `http_external`에 항목이 있지만 단순 링크(`href=`)나 `is_local`이 true | 🟡 주의 | 즉각적 위험은 낮지만 가능하면 https로 통일 권장 |

각 항목이 판정 기준에 걸리지 않으면 통과이며, 특별히 다듬을 부분이 보이지 않는 한 보고서에 🟢로 표시한다.

### 3. 보고서 작성

아래 템플릿을 그대로 사용해 한국어로 보고한다. 발견 사항이 없는 카테고리는 생략하지 말고 "해당 없음"으로 남겨 4가지를 모두 점검했다는 것을 보여준다. 모든 발견 사항에는 반드시 `파일명:라인번호` 근거를 붙인다.

```markdown
## 🔒 보안 점검 결과 — <파일명>

| 항목 | 결과 |
|---|---|
| 하드코딩된 비밀번호·API 키 | 🔴/🟡/🟢 <한 줄 설명> |
| innerHTML XSS | 🔴/🟡/🟢 <한 줄 설명> |
| console.log 민감정보 노출 | 🔴/🟡/🟢 <한 줄 설명> |
| http:// 외부 요청 | 🔴/🟡/🟢 <한 줄 설명> |

### 🔴 심각 (n건)
- `파일명:라인번호` — <무엇이 왜 문제인지, 어떻게 고치는지>

### 🟡 주의 (n건)
- `파일명:라인번호` — <무엇이 왜 문제인지, 어떻게 고치는지>

### 🟢 제안 (n건)
- `파일명:라인번호` — <개선 아이디어, 또는 "특별히 없음">
```

문제마다 "어디가 왜 문제인지"와 "어떻게 고치는지"를 한 줄로 붙인다. 예를 들어:
- 하드코딩된 키 → "환경변수나 서버 사이드 설정으로 옮기고, 이미 커밋됐다면 키를 폐기·재발급하라"
- innerHTML XSS → "`el.innerHTML = userInput` 대신 `el.textContent = userInput`을 쓰거나, HTML이 꼭 필요하면 DOMPurify 같은 라이브러리로 escape하라"
- console.log 민감정보 → "배포 전 해당 `console.log`를 제거하거나 마스킹된 값만 출력하라"
- http:// 외부 요청 → "`http://`를 `https://`로 바꿔 평문 전송을 막아라"

모든 항목이 🟢인 경우에도 표는 그대로 보여주고, "4가지 항목 모두 심각한 문제는 없습니다" 같은 한 줄 요약을 위에 덧붙인다.

## 참고

- **흔한 오탐 패턴**: 변수명에 `PASSWORD`/`KEY`가 들어가도 실제 비밀번호·API 키가 아니라 `localStorage`/`sessionStorage`의 저장 키 이름인 경우가 많다 (예: `const PASSWORD_STORAGE_KEY = 'secretNotePassword';` 처럼 이 값 자체는 `localStorage.getItem(PASSWORD_STORAGE_KEY)`에 쓰이는 키 이름일 뿐, 실제 비밀번호 값이 아니다). `hardcoded_secrets` 후보를 볼 때는 그 값이 실제로 인증에 쓰이는 값인지, 아니면 저장소 키/설정 이름인지 주변 코드를 반드시 확인하고, 후자라면 🔴가 아니라 "해당 없음"으로 처리한다.
- **흔한 오탐 패턴 2**: `xmlns='http://www.w3.org/2000/svg'`처럼 인라인 SVG/XML 안에 있는 네임스페이스 URI는 실제 네트워크 요청이 아니라 SVG/XML 규격상 고정된 식별자 문자열이다 (`https`로 바꿔도 의미가 없고, 애초에 아무 것도 요청하지 않는다). `http_external` 후보의 `snippet`에 `xmlns=`가 보이면 🔴/🟡가 아니라 "해당 없음"으로 처리한다.
- 이 스킬은 정적 분석(정규식 기반)이다. 런타임에 동적으로 조립되는 문자열, 서버에서 내려오는 값, 별도 파일로 분리된 secret 등은 스크립트가 놓칠 수 있다 — 스크립트 결과만 보고하지 말고 파일 전체를 한 번 훑어 스크립트가 놓쳤을 만한 부분이 없는지 확인한다.
- 스크립트가 없거나 Python 실행이 불가능한 환경이면, 같은 4가지 기준을 사람이 직접 파일을 읽어 눈으로 확인하되 위 심각도 표는 동일하게 적용한다.
- `page-check` 스킬과 점검 대상이 겹치지 않는다 — `page-check`는 title/링크/alt/viewport/인코딩 같은 품질 항목을, `security-check`는 이 스킬의 4가지 보안 항목을 담당한다. 둘 다 점검하고 싶다는 요청이면 두 스킬을 순서대로 실행한다.
